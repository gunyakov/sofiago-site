# sofiago-site

Каталог мест (POI) для sofiago.eu. Отдельный проект от `sofiago-vue` — не смешивать.

## Стек и архитектура

- **PHP 8.1+**, без тяжёлого фреймворка: свой роутер (`app/Core/Router.php`), PDO
  (`app/Core/DB.php`), простой `.tpl.php`-шаблонизатор (`app/Core/Template.php`).
- Страницы рендерятся на сервере (SEO) — `.tpl.php`-файлы это обычный PHP с автоэкранированием
  через `e()`. Интерактив (карта, форма добавления места, избранное) — отдельные Vue 3
  «островки» из `vue-widgets/`, собранные Vite в статику и подключаемые через `<script>`.
- **MariaDB** — схема в `database/schema.sql`, разворачивается один раз через
  `database/install.php` (см. `docs/deploy.md`).
- Почта — реальный SMTP через PHPMailer (`app/Core/Mailer.php`), не `mail()`.

## Структура

```
public/            # веб-корень (document root в HestiaCP должен указывать сюда)
  index.php         # фронт-контроллер
  assets/theme/      # статика темы ListOn (css/js/fonts/картинки)
  assets/vue/         # сюда кладутся собранные бандлы из vue-widgets/ (появится в фазе 2-3)
  uploads/            # загруженные фото объявлений/аватары
app/
  Core/              # Router, DB, Template, Session, Auth, Mailer, App, helpers.php
  Middleware/Guards.php
  Controllers/
  Models/
  templates/         # layout/, partials/, pages/, errors/, emails/
  routes.php
database/
  schema.sql
  install.php
vue-widgets/          # отдельный Vite-проект под Vue-островки
config/
  config.example.php  # скопировать в config.php и заполнить реальными данными (не коммитить)
docs/deploy.md
```

## Локальный запуск

```bash
composer install
cp config/config.example.php config/config.php   # заполнить DB/SMTP, поставить env=local
php -S localhost:8000 -t public
```

Затем один раз поднять схему БД (локально можно просто без токена через прямой запуск
`database/install.php` в CLI, либо через `?token=...` как на проде — см. `docs/deploy.md`).

## Статус

Фазы 0 и 1 готовы и развёрнуты на боевом сервере на тестовом поддомене
**https://new.sofiago.eu** (реальная MariaDB `sofiago_main`, HestiaCP):
- Фаза 0: структура, Core-классы, schema.sql, базовый layout из темы, главная с категориями.
- Фаза 1: регистрация, логин (с rate-limit на брутфорс через `login_attempts`), логаут,
  подтверждение email по ссылке, восстановление пароля — токены на паттерне
  raw-в-письме/hash-в-базе (`app/Core/SignedToken.php`), сброс пароля инвалидирует все сессии
  пользователя. Всё проверено живыми запросами на проде (регистрация → кука → dashboard →
  логаут), плюс отдельный прогон логики токенов напрямую (verify/reset/expiry).

**SMTP подключён** (2026-09-03): реальный ящик `support@sofiago.eu`. Домен `sofiago.eu` за
Cloudflare, а Cloudflare не проксирует SMTP-порты — поэтому `smtp.host` в `config.php` это
прямой origin-IP сервера, а не домен. У этого IP TLS-сертификат общий для всего VPS (выписан на
другой домен), так что `verify_peer`/`verify_peer_name` для SMTP-соединения отключены в
`Mailer.php` (только для него, не глобально) — `config.php` → `smtp.verify_tls` включит проверку
обратно, если почта когда-нибудь переедет на хостнейм с подходящим сертификатом. Порт 587
(STARTTLS) — 465 на этом сервере закрыт. Проверено реальной отправкой на боевом сервере через
`app()->mailer->send()` — письмо дошло.

**Важный найденный и исправленный баг:** PHP по умолчанию использовал UTC, а MariaDB —
системную таймзону сервера (EEST, +3) — при таком расхождении `expires_at`, посчитанный в PHP,
почти сразу оказывался "просроченным" относительно `NOW()` в MySQL. Исправлено раз и навсегда
на уровне `DB.php`/`App.php`: соединение с БД принудительно переводится в `+00:00`
(`SET time_zone`), PHP — в `date_default_timezone_set('UTC')`. Если когда-нибудь понадобится
отдельное сырое PDO-соединение мимо `Sofiago\Core\DB`, не забыть повторить это же `SET time_zone`.

Фаза 2 (публичный каталог) тоже готова и развёрнута:
- `/explore` — поиск по названию/описанию + фильтр по категории, пагинация, карта со всеми
  метками (только `status='active'`).
- `/listings/{slug}` — страница места: галерея, описание, контакты/соцсети, удобства, карта
  с одной меткой. Несуществующие/`pending`-объявления отдают 404 для анонимного пользователя.
- `/api/listings` — лёгкий JSON для карты (id/slug/title/координаты/иконка категории).
- Карта — первый настоящий Vue-островок (`vue-widgets/src/map.js`, MapLibre GL + Vue 3,
  собирается через `npm run build` в `public/assets/vue/`). Пока на публичном demo-стиле
  MapLibre — свой стиль/тайлы (как в sofiago-vue) можно подключить одной константой
  (`STYLE_URL`) позже.
- `/sitemap.xml` — генерируется на лету из БД (статичные страницы + все активные объявления).
- `database/seed-demo.sql` — 9 вымышленных demo-мест по Софии, чтобы каталог не был пустым
  до Фазы 3 (добавление объявлений). **Удалить/пересоздать перед реальным запуском.**

**Известное ограничение, не в нашей власти:** домен под Cloudflare, и `/robots.txt` на
`new.sofiago.eu` сейчас отдаёт управляемый Cloudflare контент (AI Crawl Control) поверх/вместо
ответа нашего приложения — сам маршрут `PageController::robots()` в коде рабочий и корректно
проверен на уровне origin (статический файл-заглушка от HestiaCP удалён), но переопределить
это можно только из панели Cloudflare, доступа к которой у меня нет. `/sitemap.xml` (более
важная для SEO часть) работает корректно и отдаётся именно нашим приложением.

Фаза 3 (управление объявлениями) тоже готова и развёрнута:
- `/dashboard/listings/new` и `/dashboard/listings/{id}/edit` — общая форма добавления/
  редактирования (название, категория, теги, адрес/район, точка на карте, галерея, описание,
  контакты/соцсети, удобства). Требует подтверждённый email (`Guards::requireVerifiedUser`).
- Загрузка фото — `app/Core/Upload.php`: валидация MIME/размера, на проде (есть GD) картинки
  пересжимаются в JPEG q85 с обрезкой длинной стороны до 1600px (заодно чистит EXIF/GPS);
  без GD (только в локальной разработке) файл сохраняется как есть.
- Новые Vue/JS-островки: `vue-widgets/src/gallery.js` (drag&drop превью с удалением файлов
  перед отправкой формы) и `mountPickerMap` в `map.js` (клик по карте → координаты в скрытые
  поля). Кнопка «в избранное» (`public/assets/js/favorite.js`) — сознательно обычный JS, а не
  Vue: один toggle не нуждается в реактивности.
- `/dashboard/listings` — «Мои объявления» с вкладками Активные/На модерации/Отклонённые/
  Истёкшие; `/dashboard/favorites` — избранное.
- Новое объявление всегда создаётся со статусом `pending` — попасть в публичный каталог оно
  может только после модерации (Фаза 4, которой пока нет — сейчас единственный способ
  опубликовать объявление это вручную поменять `status` в БД).

**Найденный и исправленный баг (важно для проекта на кириллице):** генерация slug для
объявлений/тегов использовала `iconv('UTF-8', 'ASCII//TRANSLIT', ...)` — на этом сервере (и
вообще много где, это зависит от locale-данных libc) кириллица через TRANSLIT превращается в
`?`, а не в что-то осмысленное, и после чистки от небуквенных символов ЛЮБОЕ кириллическое
название/тег схлопывалось в один и тот же fallback-slug → падение с `Duplicate entry` при
второй же попытке. Заменил на явную таблицу транслитерации кириллицы (болгарская/русская) —
поймал это только благодаря сквозному тесту с реальным вводом на кириллице, не по чтению кода.

Фаза 4 (модерация) готова и развёрнута:
- `/admin/listings?status=...` — очередь модерации (вкладки pending/active/rejected/expired),
  approve/reject с указанием причины, `/admin/listings/{id}/preview` — просмотр объявления
  любого статуса. Доступ — `Guards::requireAdmin()` (`users.role = 'admin'`, ставится вручную в БД).

Фаза 5 (статика/полировка, без переноса на `sofiago.eu`) готова:
- `/terms`, `/privacy` — реальные страницы вместо мёртвых ссылок в подвале (вели на 404),
  `/about` — реальный текст. Все три добавлены в `sitemap.xml`.
- **Личный кабинет и админка переехали на отдельную тему** (`app/templates/layout/dashboard.tpl.php`,
  ассеты в `public/assets/dashboard/` — родная dashboard-тема ListOn: боковой сайдбар,
  своя топбар-панель, свои цвета/шрифты), вместо того чтобы наследовать `layout/main.tpl.php`
  публичного сайта. `view()` (`app/Core/helpers.php`) теперь принимает необязательный третий
  параметр `$layout` — `Dashboard/Favorite/Admin/ListingManage`-контроллеры передают
  `'layout/dashboard.tpl.php'`, всё остальное по умолчанию продолжает рендериться в
  `layout/main.tpl.php`. Сам HTML-контент страниц (таблицы/формы/вкладки) не переписывался —
  он и раньше был на чистом Bootstrap 5, поэтому визуально подхватил стили новой темы бесплатно.
  В том же `external.html?link=...`/`&amp;`-мусоре (см. баг Google Fonts в Фазе 0-5 выше) нашлись
  ещё 3 файла внутри `public/assets/dashboard/` — почищены тем же способом.
- Логотип шапки/подвала (`logo.png`/`logo-white.png`) оказался растровой картинкой с надписью
  «List On.» — не текстом, поиском-заменой не чинится. Заменён на `partials/brand.tpl.php`:
  иконка-пин + «Sofia**GO**» тем же Caveat-акцентом, что и в сайдбаре кабинета (плюс инлайн
  `style="width:...;height:..."` на иконке — без него она плющится: у `.navbar-brand img` и
  `.footer-logo img` в теме задан только `height`, ширина брался из HTML-атрибута и не совпадал).
- Страницы ошибок (404 и остальные через `errors/generic.tpl.php`) оформлены в стиле темы —
  крупная цифра шрифтом Caveat, карточка, кнопка «На главную» — но специально СВОИМ минимальным
  инлайн-CSS (`partials/error-style.tpl.php`), без Bootstrap/темы: страница ошибки не должна
  зависеть от того, что могло сломаться. Тем же стилем оформлен родной набор HestiaCP
  `document_errors/{403,404,410,50x}.html` (отдаются nginx напрямую в обход PHP) — исходники
  лежат в `document_errors/` в репозитории, на сервере — в `~/web/<domain>/document_errors/`
  (не `public_html`/`private`, отдельная папка).

Фаза 6 (истечение объявлений) готова:
- Объявление активно 30 дней (`Listing::LIFETIME_DAYS`) с момента публикации/продления
  (`expires_at`, выставляется в `Listing::approve()` — админ публикует/владелец продлевает
  одним и тем же методом). За `Listing::RENEWAL_WINDOW_DAYS` (3) дня до истечения у владельца
  в «Моих объявлениях» и у админа в «Модерации» появляется кнопка продления («Всё ещё
  актуально» / «Продлить») — проверка окна дублируется на сервере (`Listing::isRenewable()`),
  не только скрытием кнопки в шаблоне (у админа кнопка продления доступна для активных
  объявлений всегда, без ограничения по окну — это осознанно, у владельца — строго в 3-дневном
  окне или после истечения).
- `cron/midnight.php` — CLI-скрипт вне `public/` (в `private/cron/` на сервере), пользователь
  сам добавляет в crontab на 02:00 по Софии:
  ```
  0 2 * * * /usr/bin/php /home/sofiago/web/new.sofiago.eu/private/cron/midnight.php >> /home/sofiago/web/new.sofiago.eu/private/cron/midnight.log 2>&1
  ```
  Каждый прогон: (1) переводит просроченные активные объявления в `status='expired'` (пропадают
  с карты/каталога — `search()`/`markers()` и так всегда фильтровали по `status='active'`,
  новых мест менять не пришлось); (2) шлёт письмо-предупреждение владельцам объявлений,
  входящих в 3-дневное окно, один раз (флаг `expiry_notified_at`, сбрасывается при продлении) —
  при неудачной отправке (SMTP пока не настроен) флаг не ставится, попытка повторится на
  следующую ночь автоматически. Проверено локально сквозным прогоном (истечение, письмо,
  идемпотентность повторного запуска) и один раз вручную на бою через SSH.
- Существующим активным объявлениям при миграции проставлен `expires_at = NOW() + 30 дней`
  (иначе они бы никогда не истекали и не показывали кнопку продления — `expires_at` были
  `NULL` у всех, заведённых до этой фазы).

Фаза 7 (тёмная тема, приложение, мультиязычность) готова:

- **Тёмная тема на публичном сайте — оказалась мёртвой функцией**, а не новой задачей: в теме
  уже был весь CSS (`[data-bs-theme=dark]`, 62 правила) и JS-логика (`#themeToggleBtn` в
  `theme/js/script.js`), но сам файл `script.js` никогда не подключался, а кнопки-переключателя
  не было нигде в разметке. Подключил, добавил кнопку в `nav.tpl.php`. При этом нашёл реальный
  баг: `script.js` вызывает `$(...).theiaStickySidebar()` без проверки — плагин не заинклюжен,
  бросает исключение, которое обрывает вообще весь остаток файла (включая регистрацию
  обработчика темы) — переключатель был бы всё равно мёртв. Добавил no-op шим для этого плагина
  в `main.tpl.php`, сам `script.js` не трогал. Плюс инлайн-скрипт в `<head>` против
  FOUC-мигания (тема применяется до отрисовки CSS, не после).
- **Тёмная тема в дашборде — обратная ситуация**: кнопки `.dark-button`/`.light-button` и вся
  JS-логика (переключение класса `dark` на `<html>`, `localStorage['dark-mode']`) в
  `dashboard/dist/js/app.min.js` были готовы, но самого тёмного CSS не существовало вообще —
  ни одного правила `.dark`/`html.dark` ни в `app.min.css`, ни в `style.css` (похоже, в этой
  версии темы тёмная схема для дашборда просто не входит в комплект). Написал палитру с нуля:
  `public/assets/dashboard/dist/css/custom.css` (сайдбар, топбар, карточки, таблицы, форма,
  бордеры). Добавил сами кнопки в топбар `dashboard.tpl.php` (в оригинальной ListOn-разметке
  они были, наш урезанный топбар их не унаследовал).
- **Блок «Download Our App»** — из `home-map.html`, был выброшен при построении своей темы.
  Вернул в `footer.tpl.php` (в оригинале он в подвале, показывается на каждой странице, не
  только на главной) — реальная ссылка на Google Play
  (`https://play.google.com/store/apps/details?id=eu.sofiago`), кнопка App Store оставлена
  как есть (`href="#"`, есть tooltip «Coming soon») — по требованию, ссылки на iOS пока нет.
- **Мультиязычность (en/bg/ru, по умолчанию en)** — `app/Core/Lang.php`, простые JSON-файлы
  `lang/{locale}.json` (плоский `key => строка`, паттерн из BookTorium, никакого gettext).
  Хелперы `t('some.key')`/`locale()` в `app/Core/helpers.php`. Язык выбирается через
  `?lang=en|bg|ru` (переключатель — выпадашка в шапке сайта и в топбаре кабинета), сохраняется
  в обычной cookie `sofiago_locale` на год — переживает переход между страницами и логаут.
  Переведён весь UI-«хром»: шапка/подвал, главная, каталог (`/explore`, включая переключатель
  список/плитка), карточка/страница места, все auth-страницы, весь кабинет (профиль, мои
  объявления, форма добавления/редактирования, избранное), все серверные validation/flash-
  сообщения, страницы ошибок (и динамические `errors/*.tpl.php`, и статические
  `document_errors/*.html` для HestiaCP — обновил их на английский как новый дефолт).
  **Осознанно НЕ переведено:**
  - **Контент** (названия/описания категорий, объявлений, тегов, удобств) — это данные из БД
    на одном языке, не строки интерфейса; тот же принцип, что и в любом реальном i18n.
  - **Условия использования / Политика конфиденциальности** — слишком длинный юридический
    текст, чтобы дробить на ключи; сделаны как целые отдельные шаблоны на каждый язык
    (`legal/terms-{en,bg,ru}.tpl.php`, `legal/privacy-{en,bg,ru}.tpl.php`), контроллер выбирает
    файл по `locale()`.
  - **Раздел модерации админа** (`admin/*`) — им пользуется только сам владелец сайта, оставлен
    на русском.
  - **Письма** (verify-email, reset-password, listing-expiring) — у нас нет сохранённого
    языка пользователя в БД (только cookie, которая на стороне cron/при регистрации не всегда
    доступна), а показывать письмо на языке текущей сессии сайта для другого адресата было бы
    некорректно; письма остаются на русском до отдельной задачи (нужно поле `users.locale`).
  Заодно, разбирая `/explore`, нашёл и починил настоящий баг, никак не связанный с языками:
  поиск по слову (`?q=...`) падал с `Fatal error: Invalid parameter number` **всегда**, даже
  без фильтра категории — SQL использовал один и тот же именованный плейсхолдер `:q` дважды
  (`title LIKE :q OR description LIKE :q`), а `DB.php` намеренно работает с настоящими
  серверными prepared statements (`EMULATE_PREPARES=false`), которые это не поддерживают.
  Разбито на `:q1`/`:q2`.

  берутся из аккаунта, поля скрыты) — по явному решению пользователя оставить форму как в теме.
  Публикуется только после одобрения админом (`AdminController::approveComment()`/
  `rejectComment()`, новая вкладка «Comments» в сайдбаре кабинета,
  `admin/comments.tpl.php` — по тому же паттерну, что и модерация объявлений, тоже на русском:
  панель админа не переводится, см. Фазу 7).
- **Капча — Cloudflare Turnstile** (`app/Core/Turnstile.php`): выбрана вместо reCAPTCHA, т.к.
  домен уже висит под Cloudflare — виджет создаётся в том же дашборде, без отдельной
  регистрации у Google. Проверка на сервере — `curl` на `.../turnstile/v0/siteverify` с
  секретным ключом. **Fail closed**: если `config('turnstile.secret_key')` пуст —
  `verify()` всегда возвращает `false`, форма комментария на странице места вообще не
  рендерится (`turnstileSiteKey` пуст → `<?php if ($turnstileSiteKey): ?>` не проходит) — так
  безопаснее, чем молча принимать все комментарии без защиты. **На проде сейчас так и есть**:
  ключи ещё не заведены (`config/config.example.php` → `turnstile.site_key`/`secret_key`,
  `CHANGE_ME`) — форма скрыта, до одобренных комментариев `/explore` и все listing-страницы не
  трогает. Нужно один раз зайти в Cloudflare → Turnstile → Add widget (домен `sofiago.eu`),
  вписать оба ключа в боевой `config/config.php` — после этого форма появится сама.
  Для локальной разработки использую официальные тестовые ключи Cloudflare
  (`1x00000000000000000000AA` / `1x0000000000000000000000000000000AA`) — они всегда проходят
  проверку, для прода не годятся (это открытый бэкдор, для того и существуют — только тест).
- Валидация на сервере (не только `required` в HTML): имя 2-120 символов (только для гостя),
  email — формат, если указан; текст комментария 3-2000 символов. CSRF как везде —
  `Guards::verifyCsrf()`. Проверено `curl`-ом напрямую (без браузера): пустое имя + короткий
  текст + отсутствующий `cf-turnstile-response` → 302 назад на форму с тремя ошибками, ни одна
  строка в БД не создаётся; запрос без `_csrf` вовсе → 419. Полный цикл гость → модерация →
  публикация проверен и через Playwright (форма, кнопки «Одобрить»/«Отклонить», появление
  комментария на странице места), включая тёмную тему (отдельных правил не потребовалось —
  секция использует те же бутстраповские классы, что и остальная страница).

Детали реальной раскладки на сервере — в `docs/deploy.md`.
